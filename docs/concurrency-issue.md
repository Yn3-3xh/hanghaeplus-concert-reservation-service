## 동시성 이슈 파악

* 좌석 선점(예약)
    * 여러 사용자가 동일한 좌석을 선점하려고 할 때 발생
    * 중복 선점을 방지해야 함
* 유저 포인트 잔액(추가, 사용)
    * 단일 사용자가 중복으로 포인트를 추가/사용하려고 할 때 발생
    * 포인트 잔액 불일치를 방지해야 함

## 동시성 제어 의사 결정

* 좌석 선점(예약)
  ```text
  동시성 이슈 파악: 여러 사용자가 동일한 좌석을 선점하려고 할 때 발생한다.
  
  문제: 하나의 좌석에 점유 가능한 인원은 1명인데, 2명 이상이 점유될 위험이 있다.
  
  발생 가능성: 높음
  
  재시도 필요 유무: 필요 없음
  
  해결: 분산락을 사용하여 최초 좌석 점유 이외의 요청은 예외 처리한다.
  
  선정 이유: 
    * 분산락 사용O
        여러 서버에서 동시성을 제어할 수 있도록 설계되어 있어, 하나의 좌석에 대한 요청이 동시에 들어오는 경우에도 최초 요청만을 처리하고 나머지는 예외 처리할 수 있는 강력한 방법이다. 
        이는 데이터의 일관성을 보장하고, 동시에 요청되는 좌석 선점(예약)에 따른 충돌을 효과적으로 방지할 수 있다.
    
    * 낙관적 락 사용X
        데이터 충돌 가능성이 낮고, 트랜잭션이 완료될 때까지 다른 트랜잭션이 대기하지 않도록 하여 시스템의 동시 처리 성능을 높일 수 있으나, 
        좌석 선점(예약)과 같은 경우에는 충돌 가능성이 높기 때문에 적합하지 않다.
    * 비관적 락 사용X
        데이터에 대한 접근이 이루어지기 전에 락을 설정하여 충돌을 미리 방지할 수 있으나, 락 대기 상태로 인해 성능 저하가 발생할 수 있다. 
        동시성 요청이 높다고 판단되는 좌석 선점(예약)의 모든 요청에 비관적 락을 적용하면 성능에 부정적인 영향을 미칠 수 있다.
    * kafka MQ 사용X
        좌석 선점(예약)에 대한 두 개 이상의 요청이 비동기로 처리될 때, 선점되지 않은 요청들은 해당 좌석이 예약되었는지 알 수 없다.
  ```
* 유저 포인트 충전
  ```text
  동시성 이슈 파악: 단일 사용자가 중복으로 포인트를 추가하려고 할 때 발생
  
  문제: 사용자가 의도치 않은 포인트 충전이 이루어 질 수도 있다.
  
  발생 가능성: 중간
  
  재시도 필요 유무: 필요 없음
  
  해결: 
  
  선정 이유:
    * 낙관적 락 사용O
        동시에 접근된 5번의 충전 요청에 대해서 첫번째 충전 요청만 통과시켜 준다.
        문제라고 생각한 의도에 맞도록 나머지 4번의 충전 요청은 retry할 필요없이 예외처리를 해준다.
    
    * 비관적 락 사용X
        포인트 충전에 대한 동시 접근은 막지만, 동시에 접근된 5번의 충전 요청에 대해서 락 대기를 하면서 5번 다 충전하게 된다.
        문제라고 생각한 의도와는 다른 방향이다.
    * 분산락 락 사용X
        분산된 서버에서 동시성 문제를 해결하는 데 유용하지만, 단일 사용자 충전에는 오버 엔지니어링이 될 수 있다.
    * kafka 사용X
        충전 요청을 큐에 담아 순차적으로 처리할 수 있지만, 단순한 포인트 충전 작업에 적용하기에는 불필요하게 복잡해질 수 있다.
  ```
* 유저 포인트 사용(결제)
  ```text
  동시성 이슈 파악: 단일 사용자가 중복으로 포인트를 추가하려고 할 때 발생
  
  문제: 유저의 포인트가 여러 번 차감되어 잔액이 비정상적으로 감소할 위험이 있다.
  
  발생 가능성: 높음
  
  재시도 필요 유무: 필요 없음 
  
  해결: 비관적 락을 사용하여 포인트 차감 중 다른 트랜잭션이 접근하지 못하도록 제어한다.
  
  선정 이유:
    * 비관적 락 사용O
        포인트 사용 시 다른 트랜잭션이 동일 자원이 되는 포인트에 접근하는 것을 막아 안전하게 처리할 수 있다. 
        즉, 동시 접근 방지를 해야하므로 비관적 락이 유리하다.
  
    * 낙관적 락 사용X
        충돌 가능성을 전제로 하고 충돌 시 롤백하는 방식으로 처리하므로, 자주 접근이 필요한 포인트 사용에는 적합하지 않을 수 있다.
    * 분산락 락 사용X
        분산된 환경에서 동시성 제어에 적합하나, 단일 DB 내의 자원 접근에 있어서는 비관적 락이 더 효율적이다.
    * kafka 사용X
        사용 요청을 큐에 담아 순차적으로 처리할 수 있지만, 단순한 포인트 사용 작업에 적용하기에는 불필요하게 복잡해질 수 있다.
  ```

## 동시성 제어 방식

<details>
<summary>0. Isolation Level</summary>
동시성 제어 방식에 대해 알아보기 전에 DB 격리수준에 대해 한번 짚고 넘어가고자 한다.

MySQL 기준으로 아래 표와 같다.

| **Isolation Level**              | **특징**                                                | **발생 가능 문제**                                          |
|----------------------------------|-------------------------------------------------------|-------------------------------------------------------|
| Read Uncommitted                 | 트랜잭션이 커밋되지 않은 다른 트랜잭션의 데이터도 읽을 수 있음.                  | Dirty Read,<br/>Non-repeatable Read,<br/>Phantom Read |
| Read Committed<br/>(MySQL 기본 설정) | 트랜잭션이 커밋된 데이터만 읽을 수 있음. 다른 트랜잭션에서 변경된 커밋 데이터는 볼 수 있음. | Non-repeatable Read, <br/>Phantom Read                |
| Repeatable Read                  | 트랜잭션이 시작될 때의 데이터를 보장함. 동일 트랜잭션에서 동일 쿼리 결과가 같게 유지됨.    | Phantom Read                                          |
| Serializable                     | 가장 높은 격리 수준으로, 트랜잭션이 직렬화되어 처리됨. 동시성이 많이 제한됨.          | 없음                                                    |

> Dirty Read: 커밋되지 않은 데이터가 다른 트랜잭션에 의해 읽히는 현상   
> Non-repeatable Read: 같은 트랜잭션 내에서 동일한 쿼리를 실행했을 때 다른 결과가 나타나는 현상   
> Phantom Read: 한 트랜잭션에서 같은 조건으로 조회한 결과가 다른 트랜잭션의 데이터 삽입, 삭제 등으로 달라지는 현상

<summary>1. Optimistic Lock</summary>

* 설명
  ```text
  낙관적 락이란, 트랜잭션 대부분이 충돌이 발생하지 않는다고 가정하는 방법이다.
  DB에서 사용하는 실제 락을 사용하는 것은 아니고, JPA가 제공하는 버전 관리 기능을 사용한다.
  
  SQL에서 버전 정보를 확인함으로써 실제로 데이터를 조회, 수정할 수 있는지가 결정된다.
  ```

* 동작원리
  ```mermaid
    sequenceDiagram
    title 같은 좌석에 대한 동시 예약 요청 (낙관적 락)
  
    participant RA as Request A
    participant S as Seat
    participant RB as Request B

    RA->>S: [ Begin Transaction ]
    RA->>S: 좌석 정보 조회 (버전 1)

    RB->>S: [ Begin Transaction ]
    RB->>S: 좌석 정보 조회 (버전 1)

    RA->>S: 좌석 임시 예약 요청 (버전 1, 현재 1)
    opt 낙관적 락: 버전 일치
        S-->>RA: 좌석 예약 및 결제 완료
        RA->>S: [ Commit ]
    end
    Note over RA, S: 버전 2로 업데이트

    RB->>S: 좌석 임시 예약 요청 (버전 1, 현재 2)
      Note over S, RB: 버전 충돌 감지
    opt 낙관적 락: 버전 불일치
        S-->>RB: 이미 예약된 좌석이므로 예약 실패
        RB->>S: [ Rollback ]
    end
  ```
* 장점
    * 리소스 경쟁 감소
      ```text
      DB 락을 사용하지 않아 락으로 인한 성능 저하고 작고, 동시성 처리에서 리소스 점유가 줄어든다.
      ```
    * 락으로 인한 오버헤드 감소
      ```text
      충돌이 드문 상황에서는 추가적인 오버헤드가 발생하지 않으므로, 대규모 동시 접근이 아닌 경우에 효과적이다.
      ```
* 단점
    * 충돌 발생 시 추가 로직 필요로 인한 구현 복잡도 증가
      ```text
      충돌이 발생할 경우 개발자가 직접 예외 처리를 하고, 낙관적 락을 사용하는 로직을 재시도해야 한다.
      따라서 예외 처리가 필요한 외부 요인이 존재하므로 구현 복잡도가 증가한다.
      ```
    * 충돌 증가 시 비용 증가
      ```text
      충돌이 많아지면 Race Condition(둘 이상의 스레드가 공유 데이터에 접근함으로써 생기는 문제)이 빈번하게 발생한다.
      이러한 상황에서 쿼리가 단 한번만 재수행된다고 보장할 수도 없다.(낙관적 락 대신 비관적 락이 더 적합하다.)
      ```

    * [낙관적 락과 비관적 락은 갱신 손실 문제를 어떻게 해결하는가](https://velog.io/@balparang/%EB%82%99%EA%B4%80%EC%A0%81-%EB%9D%BD%EA%B3%BC-%EB%B9%84%EA%B4%80%EC%A0%81-%EB%9D%BD%EC%9D%80-Race-Condition%EC%9D%84-%EC%96%B4%EB%96%BB%EA%B2%8C-%ED%95%B4%EA%B2%B0%ED%95%98%EB%8A%94%EA%B0%80)

<summary>2. Pessimistic Lock</summary>

* 설명
  ```text
  비관적 락이란, 트랜잭션의 충돌이 발생한다고 가정하고 데이터에 우선 락을 검으로써 데이터 정합성을 보장하는 방식이다.
  DB의 락 매커니즘에 의존한다.
  
  데이터를 조회할 때 S-Lock 또는 X-Lock을 설정하여 트랜잭션이 종료될 때까지 다른 트랜잭션이 접근하지 못하게 한다.
  이 방식은 여러 트랜잭션이 동시에 동일한 데이터를 수정할 가능성이 높은 상황에 적합하다.
  ```
* 동작원리
  ```mermaid
  sequenceDiagram
    title 같은 좌석에 대한 동시 예약 요청 (비관적 락)
    
    participant RA as Request A
    participant S as Seat
    participant RB as Request B

    RA->>S: [ Begin Transaction ]
    RA->>S: 좌석 정보 조회
    Note over RA, S: X-Lock 획득
  
    RB->>S: [ Begin Transaction ]
    RB->>S: 좌석 정보 조회
    Note over RB, S: X-Lock에 의한 대기
    RB->>S: 좌석 임시 예약 요청
  
    RA->>S: 좌석 임시 예약 요청
    S-->>RA: 좌석 예약 및 결제 완료
    RA->>S: [ Commit ]
    Note over RA, S: X-Lock 해제
    
    Note over S, RB: X-Lock 획득
    S-->>RB: 이미 예약된 좌석이므로 예약 실패
    RB->>S: [ Rollback ]
    Note over S, RB: X-Lock 해제
  ```
* 장점
    * 충돌 발생을 미연에 방지하고, 데이터의 일관성을 유지 가능
      ```text
      비관적 락은 트랜잭션이 데이터에 접근하기 전에 잠금을 설정하므로, 여러 트랜잭션이 동시에 동일한 데이터를 수정하는 상황에서 충돌을 예방할 수 있다.
      이로 인해 데이터의 일관성을 유지할 수 있다.
      ```
    * 예측 가능한 동작
      ```text
      비관적 락을 사용하면 트랜잭션이 락을 획득한 시점에서 다른 트랜잭션은 해당 데이터에 접근할 수 없기 때문에 충돌이 발생할 가능성이 낮다. 
      이로 인해 트랜잭션의 동작이 예측 가능해진다.
      ```
* 단점
    * 동시 처리 성능 저하
      ```text
      비관적 락은 자원에 대한 잠금을 설정하므로, 동시에 많은 트랜잭션이 발생할 경우 성능이 저하될 수 있다.
      특히, 트랜잭션이 잠금을 기다리는 대기 상태가 되면 전체 시스템의 처리량이 감소하게 된다.
      
      이는 비관적 락으로 인해 리소스가 점유되기 때문이다.
      따라서, 트랜잭션의 완료 시간을 지연시켜 성능이 저하된다.
      ```
    * Deadlock 발생 가능성
      ```text
      두 트랜잭션이 각각 다른 자원에 락을 획득한 상태에서 서로의 자원을 조회하려고 할 경우 데드락이 발생할 수 있다. 
      이때 각 트랜잭션은 상대방이 보유한 자원을 기다리게 되며, 무한히 대기하는 상황이 발생하게 된다.
      ```

<summary>3. Distributed Lock (Redis)</summary>

* 설명
  ```text
  분산 락은 Race Condition(둘 이상의 스레드가 공유 데이터에 접근함으로써 발생하는 문제)을 방지하고 데이터의 일관성을 유지하기 위해 원자성을 보장하는 기법이다.
  Redis는 인메모리 기반의 NoSQL 데이터베이스로, 높은 성능을 제공하여 분산 락 구현에 많이 사용된다. 
  Redis의 클라이언트 라이브러리인 Lettuce와 Redisson은 이러한 분산 락을 구현하는 데 유용하다.

  Redis는 싱글 스레드로 원자성을 보장하기 때문에 기본적으로 동시성 이슈가 발생하지 않지만, 분산 환경에서는 락 관리가 필수적이다.
  클라이언트가 락을 획득한 후 일정 시간 내에 작업을 완료해야 하며, 작업이 지연될 경우 락이 영구적으로 유지되면 다른 클라이언트가 접근할 수 없다. 
  이를 방지하기 위해 TTL을 설정하여 일정 시간이 지나면 자동으로 락이 해제되도록 해야 한다.

  추가적으로, 락을 해제할 때는 락을 획득한 클라이언트임을 확인하는 로직이 필요합니다. 
  이를 위해 락을 획득할 때 고유 ID(예: UUID)를 저장하고, 해제할 때 이 ID와 비교하여 올바른 클라이언트만 락을 해제할 수 있도록 한다. 
  락을 획득하지 못한 경우에 대한 재시도 로직을 구현하는 것도 좋은 방법이며, 클라이언트가 락을 얻지 못했을 때 일정 시간 후에 다시 시도하여 더 많은 클라이언트가 락을 획득할 수 있는 기회를 제공한다.
  ```
* 동작원리
  ```mermaid
  sequenceDiagram
  ```

1. Lettuce
    * 설명
      ```text
      Lettuce는 Redis의 Java 기반 클라이언트 라이브러리로, Redis 서버와 비동기적으로 통신하여 높은 성능과 낮은 지연 시간을 제공한다.
      분산 환경에서 자원의 일관성을 보장하기 위해 기본 Redis 명령어를 이용해 락을 구현할 수 있다.
      이 방식은 클라이언트가 락 해제 여부를 주기적으로 확인하는 스핀락 방식을 사용하여 락 상태를 관리한다.
      ```
    * 장점
        * 간단한 구현
          ```text
          Redis의 기본 명령어인 setnx와 setex를 사용해 비교적 간단하게 분산 락을 구현할 수 있어 빠르게 적용할 수 있는 장점이 있다.
          ```
    * 단점
        * 부하 증가
          ```text
          스핀락 방식을 사용하여 지속적으로 Redis에 락이 해제되었는지 확인 요청을 지속적으로 보내기 때문에 요청이 많을수록 Redis에 부하가 증가하게 된다.
          ```
2. Redisson
    * 설명
      ```text
      Redisson은 Redis를 활용한 Java 기반의 분산 락 라이브러리로, 분산 환경에서 락의 일관성을 보장하는 다양한 고급 기능을 제공한다. 
      Redis의 Pub/Sub 방식을 통해 락 해제 신호를 구독자에게 전달하여 클라이언트가 락 해제 여부를 반복 확인하지 않고도 락을 획득할 수 있다.
      또한, 다양한 락 인터페이스와 네트워크 지연 환경에서도 높은 안정성을 유지하도록 설계되었다.
      ```
    * 장점
        * 안전한 락 사용
          ```text
          별도의 Lock 인터페이스를 제공하여 락에 타임아웃을 설정할 수 있어 안전하게 락을 관리할 수 있다.
          이를 통해 분산 환경에서도 데이터 일관성을 안정적으로 유지할 수 있다.
          ```
        * 부하 감소
          ```text
          Pub/Sub 방식을 활용하여, 락 해제 시 구독 중인 클라이언트에 즉시 알림을 전달한다.
          따라서 클라이언트가 락 해제 여부를 반복적으로 요청할 필요가 없으므로, 
          Redis 서버에 대한 부하를 줄이는 효과가 있다.
          ```
        * 분산 환경에 최적화
          ```text
          분산 환경에서 다양한 고가용성 모드를 지원하여 여러 노드에 락을 분산해 안전성을 높일 수 있으며,
          네트워크 지연이 발생해도 일정 수준의 안정성을 보장한다.
          ```
    * 단점
        * 별도의 의존성 추가
          ```text
          Spring과 같은 프레임워크에서 별도의 설정이 필요하다.
          ```

<summary>4. Messaging (Kafka)</summary>

* 설명
  ```text
  (1) 카프카는 지향하는 바가 다른 메시지 큐와 다르다.
    * 실시간 데이터 피드를 관리하기 위해 통일된 높은 스루풋의 낮은 레이턴시를 지닌 플랫폼을 제공하는 것이 목표이다.
    
  (2) pub-sub 구조를 가진다.
    * 메시지를 보내는 역할과 받는 역할이 완벽하게 분리되어 있다.
    * 느슨한 결합을 통해 어느 한쪽 시스템에서 문제가 발생하더라도 서로 의존성이 없으므로 연쇄작용이 발생할 확률은 매우 낮다.
    * 컨슈머의 서버가 하나 더 추가 되더라도 카프카로만 보내면 되기 때문에 서버 추가에 대한 부담도 줄일 수 있다.
    * 하나의 토픽에 여러 프로듀서 또는 컨슈머들이 접근 가능한 구조로 되어 있다.
      따라서 하나 이상의 토픽으로 메시지를 보내거나 가져올 수 있다.
  
  (3) 디스크에 메시지를 저장한다.
    * 파티션 파일에 대해서 OS 페이지 캐시를 사용한다.
      파티션에 대한 FILE IO를 메모리단에서 처리하게 된다.
      디스크 버퍼에서 네트워크 버퍼로 직접 데이터를 복사하여 처리하게 된다.
    * 다른 message queue의 가장 큰 차이점은 통신할 때 TCP/IP 통신을 통해 바로 디스크로 쓴다는 점이다.
      다른 MessageQueue도 메모리에만 올리지 않고 설정을 통해 서버가 다운되더라도 디스크에 저장하는 설정을 할 수 있다.
      카프카는 별도의 설정없이 디스크에 적재하며, 환경설정에서 그 주기를 변경 할 수 있다.
      통신방법의 차이로 인해 (TCP/IP, APMQ) 카프카는 초당 10만건, Rabbit MQ는 초당 2만건의 데이터 처리가 가능하다.
  
  (4) 분산 환경에 특화되도록 설계되었다.
    * 하나의 카프카 클러스터는 3대의 브로커로부터 시작하여 수십대의 브로커로 확장 가능하다.
    * 확장 작업은 카프카 서비스의 중단없이 온라인 상태에서 작업이 가능하다.
    * 최초 카프카 클러스터 구성시 적은 수로 시작하더라도 이후 트래픽 및 사용량 증가로 클러스터를 확장하는 작업은 매우 간단하고, 큰 부담이 없다.
  
  (5) 클러스터 구성, fail-over, replication 같은 여러 특징을 가지고 있다.
    * 카프카는 고성능을 유지하기 위해 내부적으로 분산 처리, 배치 처리 등 다양한 기법을 사용한다.
    * 클러스터 구조의 분산 시스템은 단일 시스템보다 성능이 좋다.
  ```
* 동작원리
  ```mermaid
    sequenceDiagram
    
    participant P as Producer
    participant B as Broker
    participant C as Consumer

    P-->>B: 첫 번째 메시지 전송
    Note over B: 첫 번째 메시지 MQ 저장
    
    P-->>B: 두 번째 메시지 전송
    Note over B: 두 번째 메시지 MQ 저장

    opt
      C->>B: 첫 번째 메시지 요청
      Note over B: 첫 번째 MQ 처리
      B->>C: 첫 번째 메시지 전달
    end
    
    opt
      C->>B: 두 번째 메시지 요청
      Note over B: 두 번째 MQ 처리
      B->>C: 두 번째 메시지 전달
    end
  ```
* 장점
    * 데이터 일관성 보장
      ```text
      Kafka MQ는 순서대로 메시지를 처리하고 소비자가 정해진 규칙에 따라 메시지를 가져가도록 함으로써, 메시지의 순서와 일관성을 유지할 수 있다.
      이로 인해 다수의 요청이 같은 리소스에 접근하더라도 메시지 큐를 통해 충돌 가능성을 줄이고 데이터의 일관성을 보장한다.
      ```
    * 확장성 및 유연성 제공
      ```text
      Kafka는 분산 시스템에 적합한 확장성을 제공하여 높은 트래픽 상황에서도 성능을 유지할 수 있다.
      이를 통해 트랜잭션 처리량이 많거나 동시성 제어가 중요한 환경에서 시스템의 안정성을 확보할 수 있다.
      ```
    * 비동기 처리 가능
      ```text
      MQ는 비동기적으로 메시지를 처리하므로 요청이 여러 개 쌓이더라도 소비자들이 순차적으로 처리할 수 있다.
      따라서 트랜잭션 대기 시간을 줄이고, 자원 접근 시 생길 수 있는 충돌을 방지할 수 있다.
      ```
* 단점
    * 메시지 처리 지연 가능성
      ```text
      Kafka MQ는 비동기 큐를 통해 메시지를 처리하므로, 즉시 처리보다는 대기 후 처리되는 경우가 많다.
      따라서 실시간으로 동작해야 하는 상황에서는 일부 메시지의 지연이 발생할 수 있다.
      ```
    * 복잡한 아키텍처 구성 필요
      ```text
      Kafka를 활용한 메시징 시스템은 브로커, 프로듀서, 소비자 등의 구성 요소가 있으며, 각 역할에 맞는 설정이 필요하다.
      따라서 시스템 구성이 복잡해질 수 있고, 운영 및 유지보수 비용이 증가할 수 있다.
      ```
    * 장기 메시지 보관 부담
      ```text
      Kafka는 메시지를 저장 및 보관하기 때문에 처리되지 않은 메시지가 많아질 경우 저장소 용량을 많이 차지하게 된다.
      이로 인해 메시지를 정기적으로 삭제하거나 아카이빙하는 관리가 필요하다.
      ```
